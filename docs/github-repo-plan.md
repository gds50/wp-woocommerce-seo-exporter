# План организации открытого GitHub-репозитория

## Цель

Сделать открытый репозиторий для Python-скрипта экспорта SEO-данных из сайта на **WordPress + WooCommerce + Bono**, где:
- базовая рабочая версия уже существует;
- все последующие улучшения и тесты выполняются пошагово;
- основную доработку на сервере делает Codex;
- развитие идёт по milestone-плану без разрушения уже работающего кода.

---

## 1. Что положить в репозиторий

В репозитории должны быть:
- исходный код скрипта;
- `config.example.json`;
- `README.md`;
- `CODEX.md`;
- `docs/production-milestones.md`;
- папка `tests/`;
- `Makefile`;
- `requirements.txt`;
- `.gitignore`.

Не должны попадать в репозиторий:
- `config.json`;
- реальные пароли SSH/MySQL;
- реальные домены клиентов;
- реальные дампы БД;
- выгруженные CSV с боевыми данными.

---

seo-exporter/

## 3. Как создавать репозиторий на GitHub

### Шаг 1. Создать локальную папку проекта

```bash
mkdir seo-exporter
cd seo-exporter
```

### Шаг 2. Распаковать текущий архив проекта

Скопировать текущие файлы проекта в корень репозитория.

### Шаг 3. Инициализировать Git

```bash
git init
git add .
git commit -m "chore: initial project setup"
```

### Шаг 4. Создать пустой репозиторий на GitHub

Например:
- имя: `seo-exporter-wp-woocommerce`
- visibility: Public
- без автосоздания README, если он уже есть локально

### Шаг 5. Привязать remote и отправить код

```bash
git remote add origin <github-repo-url>
git branch -M main
git push -u origin main
```

## 4. Как работать дальше через Codex на сервере

Модель работы:
1. Ты фиксируешь milestone.
2. Codex делает только задачи текущего milestone.
3. После изменений запускаются тесты.
4. Делается commit.
5. Только потом открывается следующий milestone.

Это нужно, чтобы проект не превратился в бесконтрольный рефакторинг.

---

## 5. Правила изменений для Codex

### Разрешено
- добавлять новые файлы документации;
- добавлять тесты;
- добавлять новую функциональность внутри текущего milestone;
- исправлять явные баги;
- улучшать читаемость, если это не ломает поведение.

### Запрещено
- массово переписывать структуру проекта без отдельного milestone;
- менять интерфейс CLI без необходимости;
- удалять уже рабочие части только ради «красоты»;
- переносить код между модулями, если это не требуется текущим milestone;
- менять формат CSV без отдельного milestone.

### Базовое правило

Если улучшение можно отложить — оно переносится в следующий milestone.

---

## 6. Как оформлять доработки

Для каждого milestone Codex должен делать:

1. Краткий план.
2. Список файлов, которые будут изменены.
3. Реализацию минимально необходимого объёма.
4. Тесты.
5. Короткий changelog.
6. Commit.

Пример commit-сообщений:

```bash
git commit -m "feat(export): add wp seo query presets"
git commit -m "test(cli): cover init and run flags"
git commit -m "docs(milestones): clarify product roadmap"
```

---

## 7. Как запускать Codex на сервере безопасно

Перед каждой сессией:
- обновить `main`;
- убедиться, что рабочая ветка чистая;
- проверить наличие `config.json` только локально на сервере;
- не загружать секреты в GitHub.

Рекомендуемый цикл:

```bash
git pull
make test
# далее работа с Codex по текущему milestone
make test
git add .
git commit -m "feat(scope): milestone change"
git push
```

---

## 8. Что тестировать в первую очередь

Минимальный обязательный набор:
- загрузка `config.json`;
- генерация `QuerySpec`;
- нормализация `url`;
- валидация обязательных колонок;
- корректный exit code для `--init` / `--run` / ошибки;
- запись CSV.

---

## 9. Что считать production-готовностью

Проект можно считать близким к production, когда:
- есть preset для WordPress + WooCommerce;
- есть понятные SQL/режимы для товаров и категорий;
- есть тесты;
- есть dry-run/diagnostics;
- ошибки читаемы;
- документация полная;
- Codex может двигаться дальше только по milestone-плану.
