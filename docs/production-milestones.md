# Milestones: доведение SEO Exporter до production

## Главный принцип

**Текущее рабочее решение считается базой.**

Codex не должен ломать уже реализованное поведение, если:
- это поведение работает;
- оно покрывает текущую задачу;
- его улучшение можно перенести в следующий milestone.

Изменения, которые не являются критическими bugfix, нужно делать только в рамках соответствующего milestone.

---

## Правило non-breaking evolution

Для каждого milestone действуют правила:

1. Не удалять рабочую функциональность без крайней необходимости.
2. Не делать большой рефакторинг заранее.
3. Не менять публичное поведение CLI без явной причины.
4. Сначала расширение, потом замена.
5. Если улучшение спорное — зафиксировать в backlog следующего milestone.

## Milestone 0 — Freeze текущей базы

### Цель
Зафиксировать текущую рабочую версию как отправную точку.

### Что сделать
- проверить, что `--init` работает;
- проверить, что `--run` работает;
- сохранить пример рабочего `config.example.json`;
- описать текущее поведение в README;
- создать первичные smoke-тесты.

### Что нельзя делать
- переписывать архитектуру;
- делить файл на модули;
- менять формат CSV.

### Результат
Есть стабильная baseline-версия.

## Milestone 1 — Зафиксировать WordPress + WooCommerce + Bono контекст

### Цель
Официально оформить в документации, что проект ориентирован на WordPress + WooCommerce + Bono.

### Что сделать
- обновить README;
- добавить раздел про WordPress/WooCommerce/Bono;
- описать, что SEO-источник может зависеть от SEO-плагина;
- описать, как получать человекоподобные URL.

### Что нельзя делать
- жёстко пришивать SQL под один плагин без флага или preset;
- ломать универсальный режим.

### Результат
Документация отражает реальный целевой сценарий.

---

## Milestone 2 — Добавить WP/WooCommerce presets

### Цель
Упростить настройку для WordPress + WooCommerce.

### Что сделать
- добавить preset-конфиги или SQL-шаблоны;
- минимум: базовый preset для товаров;
- минимум: базовый preset для категорий;
- сохранить возможность ручного SQL из `config.json`.

### Что нельзя делать
- удалять кастомные SQL-запросы;
- жёстко кодировать только одну схему БД.

### Результат
Пользователь может стартовать быстрее без ручного написания SQL с нуля.

## Milestone 3 — Поддержка популярных SEO-хранилищ

### Цель
Подготовить совместимость с типовыми SEO-источниками WordPress.

### Кандидаты
- Yoast SEO
- Rank Math
- AIOSEO
- fallback на стандартные поля / кастомные SQL

### Что сделать
- определить стратегию выбора источника SEO-данных;
- задокументировать ограничения;
- добавить диагностический режим, который помогает понять, какие таблицы/мета доступны.

### Что нельзя делать
- смешивать все плагины в одну неуправляемую SQL-конструкцию;
- ломать базовый экспорт.

### Результат
Есть понятная модель выбора SEO-источника.

- проверить README;

- проверить milestone-документацию;
- оформить changelog;

## Как Codex должен работать по этому файлу

На каждом milestone:

1. Прочитать текущий milestone.
2. Работать только в его рамках.
3. Не трогать задачи следующих milestone.
4. Не делать лишний рефакторинг.
5. После изменений запускать тесты.
6. Фиксировать короткий итог изменений.

---

## Формат работы Codex для каждого milestone

```text
1. Goal
2. Constraints
3. Files to change
4. Minimal implementation
5. Tests
6. Result summary
7. Commit
```

## Отдельное правило про уже написанный код

Код, который уже написан вручную и работает, считается **защищённой базой**.

Codex может менять его только если:
- найден реальный баг;
- без изменения нельзя выполнить текущий milestone;
- изменение минимально по объёму;
- поведение остаётся обратно совместимым.

Если можно решить задачу без ломки существующего кода — нужно выбирать именно этот путь.
